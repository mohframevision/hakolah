- بيئة التشغيل السحابية بلا متصفح Chrome محلي → `npm run check:ux` (Lighthouse/axe) لا يعمل هنا. يحتاج تشغيلاً يدوياً من جهاز محمد مباشرة.

- **تحديث (2026-09-20):** نفس عطل "العملية غير مسموحة عند unlink ملف موجود بالمجلد المتصل" يتكرر أيضاً خارج git — أثناء إعادة بناء Eleventy (`npx eleventy`) على أي ملف _site موجود مسبقاً (شُوهد على `_site/css/style.css` و`_site/admin/index.html` بنفس التشغيل، بالتبادل). **الحل الأنسب المكتشف هذا التشغيل:** بدل نقل كل ملف يفشل لحاله (حلقة بلا نهاية)، انقل مجلد `_site` كاملاً باسم جديد قبل البناء (`mv _site "_to_delete/_site_old_$(date +%s)"`) ثم شغّل `npx eleventy` على مجلد فارغ تماماً — ما فيه أي ملف موجود يحتاج unlink فينجح البناء مباشرة بدون أي عطل. عيب جانبي: يترك نسخة _site قديمة كاملة بـ`_to_delete/` (بلا قيمة، نفس منطق ملفات القفل) — أضفنا `_to_delete/**` لـ`eslint.config.js` هذا التشغيل بعدما فحصها eslint بالخطأ.

**سبب `.git/index.lock` / `.git/objects/maintenance.lock` اتّضح نهائياً (2026-09-18، فحص مستقل ثانٍ بنفس الجلسة):** مو من `npx eleventy` كما كان مفترضاً. أي أمر git يمسك القفل بجلسة سحابية (`device_bash`) — `git fetch`, `git add`, وحتى `git status`/`git add -n` الجافة أحياناً — يتركه عالقاً صفري الحجم دائماً: `git` نفسه (بصلاحية المستخدم) ما يقدر يحذف ملفه الخاص اللي أنشأه للتو (`unlink: Operation not permitted`) بسبب قيود صلاحيات المجلد المتصل، مو لوجود عملية ثانية شغالة. **تأكّد تجريبياً بهذا التشغيل:** `git fetch` ترك `maintenance.lock`، وحتى `git add -n` (تجربة جافة بلا كتابة فعلية) ترك `index.lock` عالقاً من جديد فوراً بعده. **الحل اللي ينفع بجلسة سحابية بلا صلاحية حذف:** `mv` (نقل) الملف العالق بدل `rm` — النقل يمر بصلاحيات مختلفة عن الحذف بهذا المجلد المتصل فينجح دائماً حتى لو الحذف ممنوع (`mv .git/index.lock _to_delete/`). توصية دائمة لأي تشغيل قادم: لو ظهر `Operation not permitted`/`File exists` بأمر git، لا تحاول `rm` — استخدم `mv` فوراً.

**تحديث (2026-09-21):** `node scripts/minify.js` (خطوة ما بعد البناء: ضغط JS/CSS/HTML وصور `assets/uploads`) يفشل داخل بيئة `device_bash` (VM لينكس بجهاز محمد) بخطأ "Could not load the sharp module using the linux-x64 runtime" — حزمة `sharp` المثبّتة بـ`node_modules` مبنية لويندوز (npm الفعلي على الجهاز)، وVM اللينكس المستخدَم بجلساتنا السحابية لا يقدر يحمّلها. **هذا لا يؤثر على البناء الحقيقي بـGitHub Actions** (يشغّل `npm ci` على ubuntu فيثبّت نسخة linux-x64 الصحيحة تلقائياً) — قيد خاص بهذي البيئة فقط عند محاولة اختبار `npm run build`/`minify.js` كاملاً هنا. الحل المؤقت المستخدَم للتحقق من نسب الضغط: `terser`/`clean-css` (حزم JS خالصة بلا native binaries) تعملان بشكل طبيعي بهذي البيئة، فقط خطوة ضغط الصور بـ`sharp` هي المتأثرة.
- **اكتشاف (2026-09-22 11:42 UTC):** مجلد `مراجعات-يومية/` (هذا الملف وكل تقارير المراجعة) **غير مرئي إطلاقاً** لأوامر git الافتراضية بدون تحديد مسار صريح — لا `git status`/`git status -uall` ولا `git add -A .` (تجربة dry-run) يكتشفونه أو يذكرونه كملفات untracked، رغم إنه مجلد عادي تماماً (تأكّدت: ليس symlink، ليس .git متداخل، بلا قاعدة .gitignore تطابقه). **يظهر فقط** لو حُدِّد المسار صراحة (`git status -- "مراجعات-يومية"` أو `git add "مراجعات-يومية"`) — على الأغلب خلل بمسح git الشجري الافتراضي على هذا المونت الشبكي (نفس فئة أعطال unlink/EPERM الموثّقة بهذا القسم). **الأثر العملي:** أي `git add -A` مستقبلي (تفاعلي أو غير ذلك) لن يلتقط هذا المجلد تلقائياً أبداً — **السجل التاريخي كامله غير محفوظ بـgit/GitHub حالياً**، فقط على قرص جهاز محمد. صف جديد بالجدول أدناه لقرار محمد (تتبعه بـgit أم إبقاؤه محلياً عمداً).
